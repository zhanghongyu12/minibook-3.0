## 1. 背景与目标

### 1.1 用户诉求

银行卡/支付机构会把每笔消费与入账以短信推送到手机。这些短信里包含交易时间、金额、方向、渠道、卡尾号、商户，**部分银行还带账户余额**。相比 F-12/F-13（需要用户主动导出/收取账单文件），短信通道有两个独有特性：

1. **覆盖账单文件覆盖不到的渠道**：网银在线/直扣/代扣/还款等不经过支付宝或微信账户，永远不会出现在支付宝/微信账单文件里；
2. **带余额**，可用于反查「是否漏了某条通知」（§3.10）。

### 1.2 目标与可验证判定标准

| # | 目标 | 可验证判定 |
|---|---|---|
| G1 | 不遗漏 | 每次扫描满足**四类计数闭合**：`扫描总数 = 命中 + 未识别 + 非账单 + 去重/已存在`（程序内断言）；且可与短信库实计数对齐（§3.10） |
| G2 | 不烦人 | 只有**命中账单模板**的短信才产生提醒；默认**静默聚合**（不弹通知），验证码/快递/营销零提醒 |
| G3 | 不记错 | 自动写入仅限「白名单发送方 + 模板命中 + 匹配器判无重复 + 渠道允许」四条件同时满足；其余一律进待确认（§3.8） |
| G4 | 不重复入账 | 跨源（短信 ↔ 账单文件）重复可被识别：按天匹配 + 唯一候选自动判重 + 其余人工确认（§3.6） |
| G5 | 隐私最小化 | 识别成功的短信**原文不落库**；未识别样本限期保留、可一键清空（§4.2） |
| G6 | 无常驻 | 不申请前台服务/保活；广播按需拉起；被杀由补扫兜底（§3.9） |

### 1.3 明确不做（本期）

- ❌ **不抢默认短信应用**（不需要：非默认短信 App 同样能收到 `SMS_RECEIVED`，见 §2.2）；不申请 `SEND_SMS`。
- ❌ 不删除、不修改、不标记已读任何短信（只读 provider 与只读广播）。
- ❌ 不做彩信 MMS（本机 `content://mms` 为 0 行，无样本）；不做 RCS/5G消息（是否落在 `/sms` 库未实测，见 §7）。
- ❌ 首版不做通知监听（NotificationListenerService）：本机通知使用权已被 `com.xiaomi.barrage`、`com.mi.health` 占用，且侧载应用开启受限设置成本高；作为二期兜底候选。
- ❌ 不做云端上传、不做行为统计/崩溃上报。
- ❌ 不做「识别成功的短信原文入库」；不做短信全文检索。

### 1.4 通道覆盖矩阵

| 通道 | 本设计能否覆盖 | 说明 |
|---|---|---|
| 银行/支付短信（收件箱） | ✅ 主战场 | L0/L3 扫描 + L1/L2 实时 |
| 已发送/草稿/发件箱（type 2/3/4/5） | ✅ 扫描但标注来源 | 用于"转发到某号码"类场景 |
| 彩信 MMS | ❌ 本期不做 | 本机 0 条 |
| RCS / 5G消息 | ⚠️ 未实测 | 若内容不入 `/sms`，则读不到（§7） |
| 支付宝/微信 **App 内通知** | ❌ 不属于短信 | 已由 F-12/F-13 覆盖 |
| 用户主动分享/粘贴 | ✅ L4 兜底 | 零权限 |

### 2.2 短信库可达性

- 结论：**读取路径在本机成立**；但"第三方侧载 App 能否被授予 `READ_SMS`"仍属**未验证项**（§2.6）。

### 2.3 短信规模（本机，仅统计）

| 项 | 值 |
|---|---|
| 总数 | **8 条**（全为收件箱 `type=1`） |
| 时间范围 | 2026-05-07 ~ 2026-10-09（近 30 天 7 条） |
| 彩信 | 0 条 |

> 影响：本机短信量极小 → 该通道的**即时产量低**，价值主要在"补账单文件覆盖不到的渠道"与"余额链反查缺口"，而非"大量账单"。

### 2.4 时间语义（关键，决定去重精度）

- **短信内**：消息到达时间戳与正文内交易时间**逐条完全一致**（3 条格式样本：10:24/19:45/11:17 与正文「于10月8日10:24」「10月8日19:45」「10月9日11:17」一致）；
- **App 侧**：`transactions` 现有列只有 `date`（`yyyy-MM-dd`），**时分秒在解析阶段被丢弃**（`BillText.normalizeDate`：交易时间 → `yyyy-MM-dd`，PRD §F-12 口径）；但**账单文件源头是有时间的**（支付宝 CSV `yyyy-MM-dd HH:mm:ss`、微信 XLSX 为 Excel 序列号，小数部分即时刻）；
- **结论**：不加字段时，跨源匹配只能按「天」；分钟级窗口需二期加 `occurredAt`（§3.6、§7）。

### 2.5 格式示意样本（**非用户本人账单**，仅用于模板结构设计）

一条银行消费通知短信的典型结构（95526 类端口）：

```
【某某银行】您账户{卡尾号}于{M月D日H:mm}通过{渠道}支付{金额}元。活期余额{余额}元。对方户名:{商户}。
```

由该结构可得：**发送方号码 + 抬头**可作模板键；可抽取 时间 / 金额 / 方向 / 卡尾号 / 渠道 / 商户 / 余额；**无交易单号** → `externalId` 必须用内容哈希（§3.3）。
该样本的余额链自洽（`705.91 − 100.00 = 605.91`、`605.91 − 100.00 = 505.91`）→ 支持 §3.10 的余额链校验设计。
> 免责：该样本**不是**用户账单，且用户已说明无真实短信账单样本；本设计不依赖任何具体样本的字段值。

## 3. 技术方案

### 3.1 端到端流程（L0~L4）

```
[L0 手动] 导入页 →【读取短信账单】→ 权限门 → 扫描 → 干跑预览 → 确认 → 单事务入库 → 汇总
[L3 补扫] 打开 App / 解锁 / 下拉刷新 → 按水位增量扫描（覆盖关机、被清理、广播丢失）
[L1 实时] SMS_RECEIVED → 解析 → 命中账单模板 → 待确认列表（默认静默聚合，不发通知）
[L2 自动] SMS_RECEIVED → 白名单 + 模板命中 + 匹配器判无重复 + 渠道允许 → 直接写入 + 可撤销记录
[L4 兜底] 任意 App 分享文本/图片到 MiniBook → 复用解析器（零权限）
```

入库始终走既有 `ImportBillUseCase.importPrepared`（单事务 + `UNIQUE(ledgerId, externalId)` + `@Insert(IGNORE)`），**不新建第二条写库路径**。

### 3.3 关键契约

```kotlin
// 读取层输出（纯 Kotlin，无 Android 类型）
data class SmsMessageRow(
    val id: Long,             // content://sms._id
    val address: String,      // 发送方号码/端口
    val receivedAtMs: Long,   // 系统时间戳（到达时间）
    val type: Int,            // 1=收件箱 2=已发送 3=草稿 4=发件箱 5=失败 6=待发
    val subId: Int?,          // 双卡
    val body: String,
    val contentHash: String,  // sha256(address | receivedAtMs | body)
)

enum class SmsChannel { BANK_DIRECT, ALIPAY, WECHAT, OTHER }  // BANK_DIRECT=账单文件覆盖不到，允许自动

sealed interface SmsParseOutcome {
    data class Parsed(
        val row: ParsedBillRow,        // 复用 F-12 统一输出，externalId = "sms:<hash16>"
        val channel: SmsChannel,
        val cardTail: String?,
        val balanceFen: Long?,         // 余额链校验用
        val confidence: Int,           // 模板命中强度（0~3）
    ) : SmsParseOutcome
    data class Unrecognized(val reason: String) : SmsParseOutcome
    data object NotBill : SmsParseOutcome     // 判定非账单（验证码/营销/快递…）
}

data class SmsImportSummary(
    val scanTotal: Int,        // = parsed + unrecognized + notBill + skipped
    val parsed: Int,
    val unrecognized: Int,
    val notBill: Int,
    val skippedExisting: Int,  // externalId 已存在（同源幂等）
    val skippedDuplicate: Int, // 跨源判重命中
    val imported: Int,
    val existingRows: Int,     // 库里已存在（回执）
    val balanceGaps: List<String>,
) {
    init { require(scanTotal == parsed + unrecognized + notBill + skippedExisting + skippedDuplicate) }
}
```

- `externalId`：`sms:<sha256(address | yyyy-MM-dd | 规范化正文)[:16]>`（**无交易单号可用**，见 §2.5）。规范化 = 去首尾空白 + 连续空白折叠 + 全角转半角 + 去零宽字符。
- `TransactionSource` 新增 `SMS_IMPORT("sms_import")`（`source` 已是 String 列 → **无 schema 变更**）。
- 备份 JSON（F-04）**无需改动**：`source` 已是字符串字段，`TransactionSource.fromValue` 增列后即可往返（避免重演 F-12 评审 P1-1 的字段遗漏）。

### 3.4 模板注册表与解析规格

- **模板键** = 发送方号码（精确或端口前缀）+ 抬头锚点（如 `【某银行】`）。
- **抽取方式**：锚点关键字 + 结构化捕获（金额/时间/方向/卡尾号/渠道/商户/余额），**禁止整句正则**（同一银行句式会随版本变化）。
- **方向判定**：支出词表（支付/扣款/消费/还款/取现/转出…）与收入词表（入账/到账/收入/收款/存入/转入…）互斥；两者皆中或皆不中 → `Unrecognized`。
- **渠道归类**：`支付宝/财付通/微信` → `ALIPAY`/`WECHAT`（**不自动写**，§3.7）；`网银在线/直扣/代扣/还款/取现/转账/跨行` → `BANK_DIRECT`；其余 `OTHER`。
- **金额**：统一转「分」（`MoneyFormatter.toFen` 同径）；≤0 或解析失败 → `Unrecognized`。
- **多行/分段**：同一发送方在极短时间窗内的分段短信按序拼接后再解析（记录拼接次数供审计）。
- **覆盖矩阵**（发送方 × 业务类型）在实现中以注册表条目 + fixture 单测表达，每个条目必须有：命中用例、金额边界用例、方向歧义用例、格式漂移用例（应落 Unrecognized 而非误记）。

### 3.5 未识别必留痕

`Unrecognized` 与 `NotBill` 的区分必须可解释：`NotBill` 需给出判定依据（命中验证码/营销词表等），`Unrecognized` 进入**未识别清单**：

- 逐条可见（发送方、时间、脱敏摘要）；
- 可一键「手工记一笔」（预填解析到的部分字段）；
- 可「标记为非账单」（教会系统，后续同发送方同类内容直接判非账单）；
- 可「导出为 fixture」（用于补模板 + 单测回归）——实现为写 `cacheDir`，由用户主动分享/导出。

### 3.6 跨源去重（不加字段：按「天」匹配，双向共用）

**问题**：`sms:` 与 `alipay:`/`wechat:` 命名空间不同，`UNIQUE(ledgerId, externalId)` **拦不住跨源重复**。

**规则**（同一个 `SmsBillMatcher`，两个导入入口都调用 → 顺序无关）：

```
候选 = 同账本 ∧ 同方向(type) ∧ amountFen 完全相等 ∧ date(天) 相等
├─ 恰好 1 条 → 自动判重（跳过并在预览/汇总留痕：匹配到哪条、金额、日期）
├─ ≥2 条   → 进「疑似重复」人工确认（按对方名/支付方式相似度排序推荐）
└─ 0 条    → 正常入库
```

- **双向**：短信导入时反查 `alipay:`/`wechat:`/`manual` 行；账单文件导入时反查 `sms:` 行（F-12/F-13 入口接入同一匹配器）。
- **永不自动删**：只跳过或标记；用户裁决。
- **渠道抑制**（第二道防线）：`SmsChannel.ALIPAY/WECHAT` 的支出**默认不自动写**，仅提醒（这些必然被账单文件覆盖）。
- **已知盲区（必须如实告知）**：跨天错位（短信 23:59 / 账单次日 00:01、银行记账日 ≠ 支付日）会漏判 → 产生一条重复。**二期**加 `occurredAt` 列（v4 迁移）+ `±10 分钟`窗口解决；届时匹配算法不变，仅把「天相等」替换为「时间窗命中」。

### 3.7 自动化、开关与通知降噪

**开关矩阵（全部默认关闭；总开关关着时不申请任何短信权限）**

```
设置 → 短信账单
  [ ] 启用短信账单识别
  [ ] 实时识别新短信（L1）    通知方式：(•)静默聚合  ( )每日汇总  ( )逐条提醒
  [ ] 自动记账（L2）          仅白名单发送方；应用锁开启时置灰并说明原因
        白名单：<发送方> [开/关] …
  [x] 打开 App 时自动补扫（L3，默认开）
  权限状态：短信读取 [已授予/去授权] · 短信接收 [已授予/去授权] · 通知 [已授予/去授权]
```

**通知降噪（默认静默聚合）**

- 触发条件 = **命中账单模板**（不是"收到短信"）；验证码/快递/营销/运营商通知 → 零提醒；
- 默认不弹通知，只进 App 内「待确认」累积 + 图标角标；
- 可选：每日汇总（同发送方/同日合并一条）/ 逐条；
- `NotificationChannel` 分级：「待确认」= 低优先级静默；「自动记账完成」= 普通优先级；
- 已晋级白名单的发送方不再逐条提醒（已自动处理）。

### 3.8 白名单（先学会，再放手）

- **准入四条件（全部满足才自动写）**：① 发送方在 `SmsWhitelistStore` 且该项开启；② 模板命中且 `confidence` 达阈值；③ 匹配器判定无重复且渠道允许自动；④ 金额/方向健全（>0、方向明确）。
- **晋级**：预置常见端口模板（仅保证"能识别"）；用户对某发送方**手动确认入账 ≥3 次且期间无纠错** → 自动晋级。
- **降级**：用户删除/修改某笔自动记录 → 视为纠错信号 → 该发送方**立即降级回待确认**（白名单保留但 `autoEnabled=false`）。
- **可关闭**：设置页逐项开关。
- **留痕**：每笔自动写入带 `来源=短信(自动)` 标记，可在「最近自动记账」查看与撤销。

### 3.9 后台可靠性与「无常驻」口径

| 问题 | 结论 |
|---|---|
| 需要前台服务/常驻？ | **不需要**。`SMS_RECEIVED` 属隐式广播豁免项，静态注册 receiver 在进程不存在时也可被拉起 |
| 被杀是否漏？ | 单次投递可能丢 → **L3 补扫**在下次打开 App 时按水位补齐；**完整性靠补扫，及时性靠广播** |
| 写一半被杀？ | 不会：复用单事务 `importPrepared`；重投递由幂等兜底 |
| 硬约束 | **应用锁开启**时 master key 由 auth-gated Keystore key 包裹，后台无法解密开库 → L2 不可用，降级为「待确认 + 解锁后补记」（代码依据：`KeyManager` 双别名 + `AppLockController.unlock(useAuth)`） |
| HyperOS | 需引导开「自启动 + 省电无限制」；否则广播可能被拦（由 L3 兜底） |

### 3.10 「不遗漏」的三重校验

1. **四类计数闭合**（§3.3 `SmsImportSummary.init` 断言）：程序级不变量；
2. **余额链校验**：对同一卡尾号按时间排序，检查 `余额_i ± 金额 = 余额_{i+1}`；不成立即报「疑似缺口」（附时间区间）——这是短信通道**独有**的能力（账单文件无余额）；
3. **外部 oracle**（验收手段，非 App 功能）：`adb shell content query --uri content://sms` 独立统计条数，与 App 扫描数对齐（本机已验证 shell 可读，见 §2.2）。

## 4. 安全与隐私

### 4.1 权限边界（→ DEC-026）

| 权限 | 用途 | 申请时机 |
|---|---|---|
| `READ_SMS` | 扫描历史短信（L0/L3） | 仅在用户打开「启用短信账单识别」后申请 |
| `RECEIVE_SMS` | 实时识别（L1/L2） | 仅在用户开启「实时识别」后申请 |
| `POST_NOTIFICATIONS` | 通知（Android 13+ 运行时） | 仅在用户开启「实时识别」后申请 |

- 三者**可独立拒绝**，任一缺失只降级对应能力，不影响其余功能；
- 被拒/受限时的退路：① 引导到系统设置；② **L4 分享导入**（零权限）。

### 4.2 短信原文处置（→ DEC-026）

| 场景 | 处置 |
|---|---|
| 解析成功 | **只落抽取结果**；原文当次内存处理，不落库、不进日志 |
| 未识别 | 原文可**本地**保留（`noBackupFilesDir`，默认 **30 天**自动清理；设置页可「立即清空」或关闭保留） |
| 判定非账单 | 只记 `内容哈希 + 判定依据`，不留原文 |
| 去重 | 只依赖 `内容哈希` 与抽取结果 |
| 日志/通知 | **禁止**出现短信原文、卡号全文、余额；日志只允许发送方哈希前缀 + 结果类别 |

### 4.3 需同步修订的既有边界

- DEC-023（F-13 网络/凭据隐私修订）中"零敏感权限"的表述需修订：F-14 引入首个**系统敏感权限**（短信类），但仍是**用户显式开启 + 可独立拒绝 + 默认不申请**；
- `docs/05_ui.md` 的隐私说明与 `README.md`「权限与隐私」表需同步（当前只列 `INTERNET`）。

## 6. 性能设计

| 项 | 设计 |
|---|---|
| 分页 | `date ASC, _id ASC` + 批次（建议 200/批），防 CursorWindow 2MB 溢出 |
| 大批量 | 首次全量扫描可能上万条 → 进度化 + 可取消；解析走 `Dispatchers.Default` |
| 写库 | 单事务批量；已有 `@Insert(IGNORE)` 幂等 |
| 广播路径 | `goAsync()` + 超时（≤10s）+ 只处理本条（不触发全量扫描），避免 ANR/被杀 |
| 补扫 | 水位 + 重叠 3~7 天；增量条数通常为 0~几条 |
| 内存 | 不一次性持有全部原文；逐批解析后释放（解析完成即丢弃原文，仅保留抽取结果） |

### 14.4 MIUI/HyperOS 受限视图（新的能力边界，如实登记）

| 视角 | 可见短信条数 |
|---|---|
| `adb shell content query --uri content://sms`（uid 2000） | **9 条**（10010 / 10086100 / 6 个 106xxx / 1 个手机号） |
| App（持 `READ_SMS`、**非默认短信应用**）`countInProvider()` 与 L0 扫描 | **1 条**（仅普通会话 thread_id=3） |

机制：非默认短信应用的查询被 MIUI 重写为 `sms_restricted` 视图，附加
`thread_id IN (select _id from threads where private_addr_ids is null and sp_type=0)`
——即**过滤掉 `sp_type≠0` 的服务/通知类会话**（本机 8 条 10010/106xxx 通知短信对 App 不可见）。

影响与处置（→ §12.1 第 10 条、DEC-027）：

1. **「不遗漏」的分母由 ROM 决定**：§3.10 设计的 oracle 对齐（shell 计数 = App 计数）在 MIUI 上**不成立**，不得据此判定漏读；
2. 银行账单多来自 95xxx 短号，其是否落在 `sp_type=0` 暂**无样本可判**（本机无银行短信）；真实样本到位后须先验证这一点；
3. 兜底通道 = **L4 分享导入（本期未实现）**，优先级因此上调；另一条路是引导用户把本 App 设为默认短信应用（本期明确不做，架构与隐私成本过高）。

### 14.6 验收后补修：三层兜底定案（F1 修复保留 / F2 撤销）与边界短信复测（2026-10-10）

#### 14.6.1 两个「静默」缺陷（根因 → 处置）

默认通知方式是**静默聚合**（不弹通知，设计如此）。实测发现：该配置下**未白名单发送方的银行短信到达后，App 内没有任何提示**。数据没丢（短信仍在收件箱，L0 全量扫描能重新识别，已实测），但「发现」这一步断了 —— 「不会丢」不等于「不会漏」，可见性缺口等于把「不遗漏」交给用户自己想起来去点。

| 编号 | 现象 | 根因（代码事实） | 处置 |
|---|---|---|---|
| F1 | 开关叫「打开 App 时自动补扫」，实际只在**打开导入页**时触发 | `catchUp` 全仓唯一调用点是 `ImportViewModel.init`；从不进导入页的用户永远拿不到补扫兜底 | 首页 `HomeViewModel.init` 增加一次 L3 补扫（导入页那次保留：幂等）→ **已修复并保留** |
| F2 | 待确认**无任何 App 内出口**：L1 待确认只在内存、重启即归零；`SmsNotifyMode.SILENT` 的 KDoc 承诺「累计待确认 + 角标」但角标不存在；且补扫**无条件**把水位推到最新 → 未被处理的短信被水位永久越过 | ① `catchUp` 末尾 `advanceWatermark(messages.maxOf{...})` 无条件下发；② 待确认计数无承载物 | 第一版修复（2026-10-10 上午）：水位只在「已处理」上推进 + 新增 `SmsPendingTracker` + 首页角标，**已实现并验证（§14.6.2 证据）**；同日下午用户拍板**撤销**（§14.6.4） |

第一版修复**为什么不做持久化**：水位不越过待确认 ⇒ 每次开 App 补扫都会重新读到仍未处理的短信、重新计入角标 ⇒ 重启后自愈；因此无需新增表/字段，也不把短信内容或号码写进库（DEC-026 隐私边界不变）。（该设计随之撤销，见 14.6.4。）

#### 14.6.4 决策变更：撤销角标，改三层兜底（2026-10-10 下午，用户拍板）

**触发**：真机（`A1B2C3D4`，Xiaomi 某机型 / Android 16 HyperOS）上角标始终停在「短信待确认 1 条」**去不掉**。根因是**新缺陷 F3**：未识别条目的跟踪键是 `msg:<短信_id>`，而能销账的只有「确认写入」（只销已解析短信的幂等键）与「已存在/写入生效」两条路径 —— 未识别条目两者都不沾，水位又不会越过它 ⇒ 每次开 App 补扫都重新计一次，**角标常驻**（违反优先级②「不烦人」）。当时批准的补救是「进入待确认页 = 已查看 → 销账 + 水位推进」，但用户随后给出更简的最终口径：

> 「角标不要了，不需要出现已读未读的，能接收到就记账，有 App 打开扫描兜底，还有最后手动导入兜底」

**最终模型（三层兜底，不再有任何「待确认/已读」状态）**：

| 层 | 机制 | 兜的是什么 |
|---|---|---|
| ① 到达即记账 | `SmsReceivedReceiver` → `handleIncoming`（白名单四条件 + 应用锁门控） | 正常路径；能记就记，不打扰 |
| ② 打开 App 补扫 | `HomeViewModel.init` + `ImportViewModel.init` → `catchUp`（增量，读到即推进水位） | `SMS_RECEIVED` 广播丢失（进程被杀 / ROM 拦截） |
| ③ 手动导入 | 导入页「读取短信账单」→ L0 全量干跑 → 「确认写入 N 笔」 | 一切更早的历史与未处理短信，**与水位无关**，永远可找回 |

**撤销的代码（对称回退，不保留死代码）**：

| 对象 | 处置 |
|---|---|

## 16. 两种扫描方式：增量 / 全量（2026-10-10 下午，用户第三次反馈后定案；DEC-030）

### 16.1 用户口径

> 「我本次导入已经看过这条短信，并且不用处理了，下次再重新导入时候就不要再标记出来了，做两种扫描方式，
> 一种全量扫描，一种增量扫描，比如我 12:00 扫描过了，增量只扫描 12:00 以后的，只有全量的才全部扫描出来。」

拆成三条硬要求：

1. **增量 = 只扫上次扫描之后的**（用户举例：12:00 扫过 → 增量只读 12:00 之后）；
2. **全量 = 全部列出**（唯一能「把历史全翻出来」的入口）；
3. 已经看过、且不打算处理的条目，**增量模式下必须完全不出现**（不是折叠、不是灰掉，是不出现）。

**追加口径（同日 13:4x，用户看到实现后立刻纠正）**：

> 「增量扫描的时间节点不对，不应该是最后一条短信的时间，应该是当前扫描的时间。」

4. **「时间节点」= 每一次扫描的墙钟时间**，而不是「这次读到的最新一条短信的时间」。于是：本次覆盖 = 上次扫描时间之后；
   扫描完把节点更新为**本次扫描时间**。用短信时间做节点有两个实证毛病：①**空库时永远立不起水位**
   （模拟器上表现为每次增量都说「首次使用已建立水位基线」）；②节点会显示成某条旧短信的日期（真机上显示
   `05-07 15:15`），与用户「我刚才扫过」的直觉冲突。

### 16.2 实现（最小改动，复用既有水位设施）

| 层 | 改动 |
|---|---|
| `SmsBillReader` | 新增 `readAfter(watermarkMs)`：严格 `date > 水位`。**与 L3 的 `readSince` 不可混用**——后者故意回退 `OVERLAP_MS`（3 天）做容错，拿来做手动增量会把 3 天前看过的又翻出来 |
| `SmsScanMode`（新枚举） | `INCREMENTAL` / `FULL`，落在 `domain/model/SmsModels.kt` |
| `SmsScanPreview` | 新增 `scanMode` / `sinceMs`（均有默认值，既有构造点语义不变）；`assertClosed()` 不受影响 |
| `SmsBillImportUseCase.scan(ledgerId, mode)` | 增量：`readAfter(水位)` → **读完把节点推进到「本次扫描的墙钟时间」**（**不是**最后一条短信的时间，见 §16.1 追加口径）；首次无水位 → 以本次扫描时间为起点、返回空扫描。全量：`readAll()`，**不动节点**。墙钟时间在**读之前**取 ⇒ 读完到写节点之间到达的短信（时间戳晚于节点）下次仍会被读到，不丢件 |
| `catchUp`（L3 补扫） | 同样改为推进到**本次补扫的墙钟时间**（原为「读到的最新一条短信时间」）：两条增量路径写的是同一个水位，口径必须一致；补扫本身是 3 天重叠回扫，故推进到读之前的墙钟时间也不会漏 |
| 导入页入口卡 | 短信卡两个按钮：`增量扫描`（主）/ `全量扫描`（次）+ 一行小字说明差别 |
| 预览页 | stepper 下方一行「扫描方式说明」：全量 → `全量扫描：列出全部历史短信`；增量 → `增量扫描：本次覆盖 MM-dd HH:mm 之后的新短信，起点已更新为 MM-dd HH:mm`（首次 → `增量扫描：首次使用，起点已设为本次扫描时间 MM-dd HH:mm（历史短信请用「全量扫描」）`）。**只有时间戳进文案，不含任何短信内容**（DEC-026） |
| 「重新扫描」 | 沿用当前模式（模式从 `preview.scanMode` 读回）；切模式 = 顶栏 ← 回入口页再选 |

### 16.3 与既有三层兜底的关系（不遗漏不破）

- 增量**跳过**的历史永远不会消失：全量扫描随时可重新列出（含 `▸ 此前已看过 N 条` 折叠区），全程不删件、不过滤；
- 打开 App / 进入导入页的 **L3 静默补扫同样推进节点**（也已统一为墙钟时间），因此「增量」通常只显示「刚到达、还没被任何一层处理过」的短信；要核对全部请用全量；
