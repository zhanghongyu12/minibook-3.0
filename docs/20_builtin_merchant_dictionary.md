# 20 · 内置商户词典（docs/15 第 7 条）

> 状态：**已实施（2026-10-13）**。需求登记与演进见 `docs/15_category_rule_fuzzy_match_plan.md` 第 7 条。

## 1. 背景与用户口径

用户原话（2026-10-13）：

> 「我想的是我测试的面肯定不够，比如我测不到罗森属于什么，内置肯定没有，另外一个人用了就归为其他，
> 这时候那个人把他归为餐饮，下一个人再用就知道这是餐饮」（众包设想）

> 「能不能联网搜索一波大的，然后当做内置的，然后学习的就都在 app 本地」（最终定案）

**最终形态**：不做众包/上传（零上传、零隐私风险、不需要账号、离线优先），改为**内置商户词典**——
一份「商户/品牌关键词 → 内置分类」的静态清单随 App 打包；「学习」完全留在本地（自学习规则仍是第一优先级）。

## 2. 实现

### 资源

- `app/src/main/res/raw/merchant_dictionary.json`：`{"version": 1, "note": …, "entries": [{keyword, category}]}`
  - **1315 条**、关键词全唯一、70,105 字节（约 68 KB）；APK 增重 <0.2 MB（现约 39 MB）。
  - 打包在 APK 内、**不解压**到数据目录（不占 `/data/data`）；首次使用装载进内存（几百 KB）。
  - 离线可用；升级 App 即更新，无需任何网络。

### 代码

- `domain/usecase/category/MerchantDictionary.kt`：接口 `ensureLoaded()` + `suggest(counterparty): String?`。
- `domain/usecase/category/BuiltInMerchantDictionary.kt`：进程内注册表 + 匹配器（纯 Kotlin、JVM 可测）：
  - 匹配与自学习规则共用同一套 `CategoryRuleNormalizer`（docs/19）；
  - ① 归一化后**完全相等** → 命中（如「罗森(北京)有限公司房山店」归一化「罗森房山店」== 词典词）；
  - ② 归一化后**包含** → 命中，取关键词**最长**者（更具体的品牌优先，如「星巴克臻选」先于「星巴克」）；
  - 已装载条目按归一化关键词长度降序，最长先试。
- `data/local/dictionary/MerchantDictionaryJson.kt` + `MerchantDictionaryStore.kt`：读 `res/raw` JSON 并装载（I/O 在 data 层；失败静默——词典只是建议，绝不应阻断导入主流程）。
- `domain/usecase/bill/ImportBillUseCase.kt` 步骤 1.5：`resolveCategoryId` 的自学习规则之后、类型映射之前查词典建议；
  词典建议只在 `allowWeakRuleMatch = true`（用户看得见、改得动的预览/手工确认路径）生效；
  **L2 到达即记账不查词典**——防止全局词典把某一笔静默写错（优先级①「不写错账」）。

### 优先级（总）

`本地学习 > 内置词典 > 内置类型映射 > 其他`；词典与自学习都未覆盖的长尾落「其他」+ 本地学习兜底。

## 4. 维护方法

1. 编辑 `merchant_dictionary.json`（保持 `keyword` 唯一、`category` 为内置分类名之一）；
2. 跑单测（`MerchantDictionaryTest`：每条映射到合法内置分类、无重复关键词、匹配器命中/不命中样例）；
3. 新增词条无需改代码（匹配器按长度降序自动生效）。

## 5. 诚实边界（种子集，不是全集）

- 词表覆盖的是**常见全国性品牌/商户**；区域小商户、冷门行业大概率不在词表内——它们照旧落「其他」+ 本地学习，不受影响；
- 分类是按品牌名推断的**行业默认**，可能与个人记账习惯不一致——词典建议**始终可见、可改**（预览路径），不静默写入；
- 词表未经真实账单全量验证；识别率是「对已覆盖商户」的局部指标，未做整体宣称；
- 关键词可能随时间过时（门店更名/品牌并购）——词典是静态快照，准确性依赖随版本更新。
