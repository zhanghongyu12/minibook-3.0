### 4. 两条贷款营销短信被判成账单（398000 元）· **缺陷 · P0**

**你的原话（两条原文）**
```
【农商银行】您好，我行授予您398000元，于6月30日停办，可用于日常消费，房屋装修，生意应急
回6查利息 / 回8确认金额 / 拒收请回复R

【建设银行】尊敬的客户，我行可特批您398000元周转款，三年内灵活借还，5月16日截止，请及时回复
回1查询利息 / 回2办理 / 拒收请回复R
```

**现象**：两条被当成账单解析出来（一条按**支出**、一条按**收入**），金额取的是"授信额度"398000 元。

**根因（已定位）**
1. **方向词先判、营销过滤后判**（[SmsBillParser.kt:88–107](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L88-L107)）：只有方向词都没命中才会去查营销词表。样本 1 含「**消费**」（"可用于日常消费"）命中支出词表；样本 2 含「**利息**」（"查询利息"）命中收入词表 → 直接放行。
2. **营销词表不覆盖授信话术**（[SmsBillParser.kt:43–46](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L43-L46)）：没有 授予/特批/授信/额度/周转款/停办/截止/回复R/拒收请回复R 这类词。
3. **金额取了授信额度**：`398000元` 前面没有"余额/额度"字样（[BALANCE_CONTEXT](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L48-L49)）→ 被当成交易金额（[L110–118](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L110-L118)）。

**影响**：账本里存在 398000 元级的假记录 → 污染结余 / 报表 / 分类统计。

**你的反馈（2026-10-10）**：**「账单内确实有数据」** ⇒ 这两条已被写入，属**脏数据，待处理**。

**待办（两条线）**
1. **处理脏数据**（需要你操作，**我不擅自动你的数据**）：全部交易 → 搜「398000」→ 看有几条、什么类型（预计 1~2 条：一条支出、一条收入）→ 在 App 内**编辑成正确内容或删除**；删完结余与报表会自动修正。
2. **修解析**（正式改动时）：登记在案（根因见上）；修好后这类授信/营销短信会归入"非账单"，不再入账。

**待你补充**：搜到几条、金额与类型分别是什么（用来界定脏数据范围）。

### 5. 日期选择器缺少联动约束 · **缺陷 · P1**

**你的原话**
> 「账单筛选日期逻辑不对，结束日期能晚于开始日期。」

**你的澄清（2026-10-10）**
> 「选择器就不对，第一个框我选择了 10月10日，后面框应该只能选择日期之后的，不可以再选 10月1日」

⇒ 诉求明确：**两个日期选择器要联动约束**——起始日选定 10-10 后，结束日的可选范围只能是 **≥ 10-10**（不允许再选 10-01）；对称地，结束日选定后，起始日也不该能选到它之后。

**现状（已核对）**
- 起止两个日期**各自独立可选、没有任何约束** → 允许出现"止 < 起"。
- SQL 是闭区间，**止 < 起 时静默返回空列表**，界面不给任何解释。
- 日期↔毫秒转换两端都用 UTC，**已排除"选完日期跳一天"**这一类原因。

**代码证据**：[TransactionsScreen.kt:496–505](app/src/main/java/com/minibook/ui/transactions/TransactionsScreen.kt#L496-L505) + [TransactionsViewModel.kt:193–196](app/src/main/java/com/minibook/ui/transactions/TransactionsViewModel.kt#L193-L196)（无校验）、[TransactionDao.kt:106–107](app/src/main/java/com/minibook/data/local/db/dao/TransactionDao.kt#L106-L107)（闭区间 SQL）、搜索页同款筛选 [SearchConditionComponents.kt:70–130](app/src/main/java/com/minibook/ui/search/components/SearchConditionComponents.kt#L70-L130)、日期转换 [Pickers.kt:156–171](app/src/main/java/com/minibook/ui/components/Pickers.kt#L156-L171)（UTC）。

### 6. 退款被记成支出，且与支付两条无法区分 · **缺陷 · P0**

**你的原话（两条原文）**
```
【北京银行】您账户3170于10月5日21:49通过网银在线（京东支付）退款80.40元。活期余额1149.48元。对方户名:露露京东自营旗舰店。
【北京银行】您账户3170于10月5日21:45通过网银在线（京东支付）支付80.40元。活期余额1069.08元。对方户名:露露京东自营旗舰店。
```

**现象**：两条在列表里**看起来一模一样**（同金额 80.40、同日期、同商户、同摘要），且退款那条被记成**支出** → 支出被重复计了一次。

**根因（已定位）**
1. **「退款」被列在支出词表里**（[SmsBillParser.kt:28–30](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L28-L30)）→ 退款短信判支出；而微信导入口径里退款是**收入**（[BillCategoryMapping.kt:51–52](app/src/main/java/com/minibook/domain/model/BillCategoryMapping.kt#L51-L52)）→ 口径不一致。
2. **两条不可区分**：`date` 只到日（[SmsBillParser.kt:21](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L21)「时分秒丢弃」），摘要只拼「短信消费/短信入账·尾号·渠道」，**不含时间、不含退款标记**（[L351–364](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L351-L364)）。
3. **两条都入库本身是对的**：`externalId` 用「发送方+日期+正文」哈希，两条正文不同 ⇒ 不算重复（[L372–384](app/src/main/java/com/minibook/domain/usecase/sms/SmsBillParser.kt#L372-L384)）。问题只在"方向判错 + 不可区分"。

**影响**：已写入的错误行需要修正（你决定改还是删，**我不擅自动数据**）。

**待你拍板**：退款该记成 **收入**（与原支付相抵）／ **红冲原支付** ／ **不计收支** 哪种？（正式改动时再设计实现。）
